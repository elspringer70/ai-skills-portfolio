JIRA Ticket Breakdown

A repo-scoped Codex skill that turns PRDs, feature briefs, meeting notes, and other product context into structured ticket drafts for human review.

See documented example View SKILL.md
Implementation Codex Agent Skill
Interface Codex conversation
Output Markdown ticket drafts
JIRA connection None
Approval Human required
Implementation boundary

This project does not create or update JIRA issues. It generates drafts that a person reviews, revises, and manually moves into a ticketing workflow.

Synthetic fintech feature brief View full source

Income verification before credit-offer acceptance

Customers can currently see an estimated offer after a short eligibility form. Compliance wants clearer language that the offer is not final until income verification is complete.

Stakeholder context

  • Engineering can use the existing verification provider.
  • The provider may return approved, rejected, or manual review.
  • Support has seen customers interpret pre-qualification as guaranteed approval.
  • Data needs events when verification starts and completes.

Constraints

  • Launch behind a feature flag.
  • Do not change the pre-qualification form.
  • Compliance must approve customer-facing copy.

In scope: Confirmation step, provider handoff, approved/rejected/manual-review states, analytics events, feature flag, and compliance-approved copy.

Example story

Title: Add manual review state for income verification

As a customer whose verification requires manual review, I want to know what happens next so that I am not left waiting without context.

Acceptance criteria excerpt

  • When the provider returns manual review, the application displays a pending-review state.
  • The customer cannot continue to final offer details while review is pending.
  • The application records a completion event with status manual_review.
  • Customer-facing language requires compliance approval.

Open question

Should customers receive an email or in-app notification when manual review completes?

How it works

Instructions make the workflow repeatable; a person remains responsible for the tickets.

01

Read the supplied context

Codex extracts confirmed goals, users, scope, constraints, risks, and missing information from material supplied in the conversation or workspace.

02

Separate facts from assumptions

Material unknowns become clarifying questions. Draftable gaps remain visible as assumptions or open questions instead of becoming invented requirements.

03

Structure the ticket package

The skill produces an epic, user stories, acceptance criteria, edge cases, dependencies, risks, engineering tasks, suggested metadata, and a readiness assessment.

04

Apply the evaluation rubric

The checked-in rubric tests product understanding, ticket quality, acceptance criteria, risk detection, questions, and JIRA readiness.

05

Hand off for human review

The final artifact is Markdown. A product manager and relevant partners decide what to change, approve, or enter into JIRA.

Model

The repository does not pin a model. The skill runs in Codex using the model available in that session.

Tools

Local file reading and Markdown output. Supporting portfolio files provide examples and evaluation guidance.

Integrations

None in this version. The repository discusses possible JIRA and documentation integrations but does not implement them.

Human approval

Required. The skill labels drafts for review and explicitly states that no JIRA issues were created or updated.

What I learned

The useful part is not producing more tickets. It is making uncertainty visible.

Challenge

Ambiguity hides inside polished requirements

A draft can sound complete while still missing ownership, error behavior, regulated copy, data handling, or a definition of success. The skill has to distinguish a missing decision from a requirement it is allowed to infer.

Design choice

Readiness is part of the output

Each story and package can be marked ready, needs clarification, or blocked. That makes the artifact useful for refinement even when it is not ready for implementation.

Limitation

Quality still depends on source context

The skill cannot recover product decisions that were never supplied. It can expose gaps and ask better questions, but a human still owns the answers and final scope.

Limitation

No connected delivery workflow

The current version does not read a live backlog, create JIRA issues, resolve dependencies, or verify implementation. It produces reviewable Markdown only.

Next improvement

Add repeatable evaluation cases

The rubric exists, but future work could add a small test set covering vague requests, API-heavy changes, and regulated lending flows to compare revisions systematically.

Takeaway

Guardrails make the skill more credible

Explicitly refusing to invent business rules or claim JIRA writes is as important as the ticket format. The boundary makes the workflow easier to trust and review.
